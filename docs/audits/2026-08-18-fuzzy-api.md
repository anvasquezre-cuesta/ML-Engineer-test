## Verdict

**No P0 in this scope.** The graded fuzzy-matching traps are all handled correctly and I verified each one by running the real service: matching is full-string (`fuzz.ratio` on both normalised strings, `fuzzy_service.py:42` — *not* `partial_ratio`/`WRatio`, which would have inflated `"Maria"` vs `"María González"` to 90/100), case-insensitive and accent-insensitive (NFKD + combining-mark strip + `casefold`, `text_normalization.py:12-18`), tolerant of OCR noise (`Maria Gonzaiez` → 0.93 → matched), correctly rejects an unrelated name (`Robert Johnson` → 0.42), and emits scores already divided by 100 so they satisfy the `ge=0, le=1` contract in `schemas.py:29`. The threshold is config-driven (`fuzzy_match_threshold=0.90`) and applied as `>=`. Uploads are rejected by **content** (`%PDF-` magic + a real PyMuPDF parse + `needs_pass` + `page_count`), empty uploads are rejected, the file handle is closed in a `finally`, `names` is parsed defensively into 400/422, the router is thin and depends on the `ExtractionService` Protocol, the heavy sync pipeline runs off the event loop (verified: `extract` executes on an "AnyIO worker thread"), error→status mapping is meaningful (503/500) and leaks nothing to the client, and a zero-result document returns a 200 with empty lists. `59 passed` on the existing suite. What is left is a set of five P1 robustness gaps — one uncaught `RecursionError` that turns a malformed `names` field into an unauthenticated **500**, no bound on pre-buffered upload size or on PDF page count, no serialisation of the cold-start model build, and an order-sensitive similarity function that drops the common `"Last, First"` rendering — plus eight P2 polish items. This is well above the usual bar for a take-home; every finding is an incremental hardening, not a rewrite.

## Findings

| ID | Sev | File:line | Problem | Recommended fix |
|---|---|---|---|---|
| F-01 | P1 | `app/services/fuzzy_service.py:42` | `fuzz.ratio` is token-**order** and token-**count** sensitive. Measured against query `María González`: `"Gonzalez, Maria"` → **0.57 (dropped)**, `"Maria Isabel Gonzalez"` → **0.80 (dropped)**, `"Ana Maria Gonzalez Perez"` → 0.74. `"Last, First"` is how a huge fraction of scanned KYC/contract forms print names, so this is a realistic false-negative class. | Score with `max(fuzz.ratio(a, b), fuzz.token_sort_ratio(a, b)) / 100`. Measured: lifts `"Gonzalez, Maria"` 57→100 while keeping `"Maria"` at 53, `"Gonzalez"` at 73 and `"Robert Johnson"` at 29 — i.e. it fixes order without the substring inflation the README warns about (`WRatio` gives `"Maria"` 90, `partial_ratio` 100). Do **not** use `token_set_ratio` (it scores bare `"Maria"` 100). |
| F-02 | P1 | `app/api/validation.py:31-38` | `json.loads` is guarded only against `JSONDecodeError`. `names = "[" * 3000 + "]" * 3000` raises `RecursionError`, which nothing catches → the client gets **HTTP 500 `Internal Server Error`** (verified end-to-end through the ASGI app). A client-supplied string must never produce a 5xx. | `except (ValueError, RecursionError) as exc:` → 400, and cheaply pre-check `len(raw_names)` against a new `max_names_payload_bytes` setting before parsing. |
| F-03 | P1 | `app/api/validation.py:116-156`; no middleware in `app/main.py:22-56` | The 413 is enforced only *after* Starlette has fully buffered the body: `pdf_file.size` (line 123) is populated only once the part is completely written to the `SpooledTemporaryFile`, which spills to **disk** above 1 MB. A 5 GB upload is therefore written to disk in full before being rejected. The in-process copy *is* bounded correctly (`read(max_size_bytes + 1)`, line 135), so this is a disk/IO exhaustion vector, not a heap one. | Add an ASGI middleware that rejects `Content-Length > settings.max_upload_size_bytes` with 413 before the body is consumed; keep the existing post-read check as defence in depth (it already correctly catches a lying `Content-Length` — verified). |
| F-04 | P1 | `app/api/validation.py:82-113`; `app/config.py:16-27` (no page limit) | No bound on the *work* a valid PDF implies. An **828 KB** blank PDF containing **5000 pages** passes `validate_pdf_content` (verified). At `ocr_dpi=300` with `ocr_timeout_seconds=60` *per page*, one such request can hold an AnyIO worker thread for hours; there are only 40 such threads (verified default limiter = 40). Neither `extract.py` nor `extraction_service.py` imposes a total deadline. | Add `max_pdf_pages` to `Settings`, assert `document.page_count <= max_pdf_pages` inside the `pymupdf.open` block at line 100, and add a wall-clock budget in `DocumentExtractionService.extract` that raises a mapped error once exceeded. |
| F-05 | P1 | `app/api/dependencies.py:16-21` | `@lru_cache` does **not** serialise concurrent cold calls, and FastAPI executes this *sync* dependency on an AnyIO worker thread. Measured: 8 concurrent first-requests invoked `build_extraction_service` **8 times**. On a real cold start that is 8 simultaneous spaCy + Tesseract initialisations. Secondary effect: models load on the first *request*, so the first user pays multi-second latency and a missing `en_core_web_sm` surfaces as a per-request 503 instead of a startup failure. | Build the pipeline once in a FastAPI `lifespan` handler, store it on `app.state`, and have `get_extraction_service` just read it (still overridable via `dependency_overrides`). Minimal alternative: wrap the build in a module-level `threading.Lock`. |
| F-06 | P2 | `app/api/dependencies.py:16`, `app/services/factory.py:12-20` | One service instance is shared by up to 40 AnyIO worker threads with no concurrency bound. `SpacyNERService._nlp` (`ner_service.py:29`) is shared model state, and spaCy `Language` objects are not documented as thread-safe for concurrent `__call__`. I did not reproduce a corruption — flagging the structural risk, not an observed failure. | Bound pipeline concurrency with a semaphore sized from config (also caps memory), or hold one NER instance per worker thread. |
| F-07 | P2 | `app/api/validation.py:196-200` (`validate_extraction_request`) | The PDF is read *and fully parsed by PyMuPDF* before `names` is validated, so a request with a malformed `names` field pays the entire PDF cost first (confirmed: `bad pdf + bad names` returns the PDF error). Also, the only cap on the `names` field size is Starlette's implicit 1 MB `max_part_size` (`400 "Part exceeded maximum size of 1024KB."`), not `settings.max_names_per_request`. | Call `parse_names` (cheap) before `read_and_validate_pdf`, and make the payload cap explicit in `Settings`. |
| F-08 | P2 | `app/api/validation.py:134-141` | The blanket `except Exception` around `pdf_file.read()` maps **every** read failure to 400, including server-side spool/disk errors that are not the client's fault. | Map `ClientDisconnect` / multipart errors to 400 and let genuinely unexpected I/O errors become 500 so they are alertable. |
| F-09 | P2 | `app/api/extract.py:53-58` | The terminal `except Exception` also catches `HTTPException` (it is an `Exception` subclass), so any deliberate status raised deeper in the stack would be flattened into a generic 500. | Add `except HTTPException: raise` immediately before it. |
| F-10 | P2 | `app/services/extraction_service.py:69-71` + `app/api/extract.py:42,48,54` | Every pipeline failure is logged with a full traceback **twice** — once by the service (`logger.exception`) and again by the router. Doubles log volume and splits one incident across two records. | Log the traceback once at the HTTP boundary; in the service, log the `stage` at WARNING (or attach it to the exception) and re-raise. |
| F-11 | P2 | `app/main.py:15-18,25-52` | Logging is human-readable text (`%(asctime)s \| %(levelname)s \| ...`), not structured, and carries no request/correlation ID, so the per-stage lines of concurrent requests cannot be tied to one request. The rubric grades "structured logging with useful context". | Emit JSON (`python-json-logger` or a custom `Formatter`) and set a `request_id` contextvar in the middleware at line 26, injected into every record. |
| F-12 | P2 | `app/api/dependencies.py:21` | `get_extraction_service` calls `get_settings()` directly rather than receiving it through `Depends`, unlike `validation.py:170`. A test or deployment that overrides `dependency_overrides[get_settings]` therefore does not affect how the pipeline is built. | `def get_extraction_service(settings: Annotated[Settings, Depends(get_settings)])`. |
| F-13 | P2 | `app/main.py:55-61` | No `CORSMiddleware`. The README's bonus "audit viewer" is explicitly a browser page that calls `/api/extract`; served from `file://` or any other origin it will be blocked. | Add `CORSMiddleware` with an origin list from `Settings`, or serve the viewer as a static file from the app itself. |

### Areas checked and found clean

* **Score normalisation** — `fuzzy_service.py:42` divides by 100 before constructing `FuzzyMatch`; parametrised test at `tests/test_fuzzy_service.py:77-84` locks it in. No `0..100` schema violation.
* **Threshold semantics** — `>=` at `fuzzy_service.py:47`, default `0.90` from `config.py:25`, env-overridable via `DOC_INTEL_FUZZY_MATCH_THRESHOLD`. Not hardcoded.
* **Best-match-only** — the inner loop keeps a single best candidate per extracted occurrence (`fuzzy_service.py:39-45`); repeated occurrences of the same name intentionally produce one match each, which is consistent with `extracted_names` being per-occurrence and is asserted at `tests/test_fuzzy_service.py:60-66`.
* **No silent failure swallowing** — `grep` over all in-scope files found no `except: pass`; the only broad handler that does not re-raise (`validation.py:163`) logs with `exc_info=True`.
* **Information leakage** — all client-facing details are generic (`"document extraction failed"`, `"an extraction dependency is unavailable"`); the uncaught-`RecursionError` path returns Starlette's plain `Internal Server Error` with no traceback in the body.
* **Zero-result degradation** — verified against the *real* `DocumentExtractionService` + real fuzzy service: an empty page yields `{'extracted_names': [], 'fuzzy_matches': []}`, i.e. 200 with empty lists, not an error.
* **Handle/temp-file hygiene** — `read_and_validate_pdf`'s `finally` closes the upload on every path (verified `upload.file.closed is True` for the success, empty, and both oversize paths); `validate_pdf_content` uses `with pymupdf.open(...)`; no `tempfile` is created by this layer.

## What is already good

1. **The fuzzy scorer is the right one for the rubric.** `fuzz.ratio` on two fully normalised strings (`fuzzy_service.py:42`) — the exact opposite of the `partial_ratio`/substring trick the README warns about. The evidence table in §3 shows `WRatio`/`partial_ratio` would have scored a bare `"Maria"` at 90/100 against `"María González"`; this implementation scores it 53 and correctly drops it.
2. **Normalisation is genuinely well built** (`text_normalization.py:9-19`): NFKD → drop combining marks → `casefold()` (not `.lower()`, so `ß`→`ss` works) → collapse all punctuation/underscores to spaces → collapse whitespace. Shared with the bbox layer, so matching and locating agree on what a "name" is.
3. **Scores already satisfy the fixed schema** (`/100` before `FuzzyMatch`), with a parametrised regression test across thresholds 0/0.5/1.
4. **Content-based PDF rejection done properly** — magic bytes *and* a real PyMuPDF parse *and* `needs_pass` *and* `page_count == 0`, mapped to distinct, meaningful statuses (415 vs 400 vs 413). `tests/test_request_validation.py:56-71` specifically proves a `.pdf` filename with `application/pdf` content-type does not rescue non-PDF bytes.
5. **Bounded read + guaranteed close.** `read(max_size_bytes + 1)` never trusts the declared size, and the `finally` at `validation.py:160-164` closes the upload on every exit path, including exceptions.
6. **`names` parsing is defensive and returns the right class of error** across ~14 malformed shapes (§4), with 400 for syntax and 422 for semantics.
7. **Clean DI and seams.** `protocols.py` defines four narrow, `runtime_checkable` Protocols; `factory.py` is a genuine composition root; `DocumentExtractionService` takes all four collaborators by constructor injection and holds no global state; `tests/test_extraction_service.py` exercises the whole orchestration with four fakes and no HTTP at all.
8. **The router is genuinely thin** (`extract.py`, 58 lines, no business logic) and the heavy sync pipeline is correctly dispatched with `run_in_threadpool`, verified to execute off the event loop.
9. **Error taxonomy is deliberate.** `errors.py` separates dependency failures (→503) from pipeline failures (→500), and `extract.py` maps them with generic client-facing text while logging the real traceback server-side. All four branches are covered by tests.
10. **Zero-result degradation is correct** — 200 with empty lists, verified against the real service, not a stub.
11. **Useful operational logging already exists**: per-stage timings, page/mention/match counts, and a `stage` marker on failure — and it deliberately logs counts rather than the names themselves, which is the right call for PII.
